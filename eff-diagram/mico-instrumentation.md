# mico 可评估性打点清单

产品站交付效率度量 · 数据底座需求 · 2026-09-10

目标：mico 落地后，效率度量体系全部指标可从事件流自动计算，延期归因自动判定、零人工补录。本文是给 mico 设计的最小打点需求；报告层（①②③④、三个数、四识别）不变——mico 是数据层升级，不是模型重做。

飞书文档「产品站需求交付效率度量体系 · 一页纸」🛰️ 节为本文的精简版。

## 一、最小事件集（9 种）

### A. 里程碑事件 —— 分段端点

| # | 事件 | 对应现 bitable 字段 | 采集方式 |
|---|-----|-----|-----|
| 1 | 计划设计稿交付（承诺） | 计划设计稿交付时间 | 排期时人工录入（承诺类，仅 1、2 手填） |
| 2 | 交付运营（承诺上线日） | 交付运营时间 | 同上 |
| 3 | 开发介入 | 开发介入时间 | 首次 commit / 任务认领，自动 |
| 4 | 提测 | 提测时间 | 提测单 / 流水线，自动 |
| 5 | 可交付 | 可交付时间 | 验收通过动作，自动 |
| 6 | 实际上线 | 实际上线时间 | 发布流水线，自动 |

### B. 行为事件 —— 提测后黑箱 ＋ 归因依据

| # | 事件 | 关键区分 | 采集方式 |
|---|-----|-----|-----|
| 7 | 问题修复 | 发起方＝测试（提出）/ 研发（修复） | bug 系统状态流转 webhook，自动 |
| 8 | 需求变更 | 发起方＝需求方 | 需求方在 mico 内一键申报，禁研发代填 |
| 9 | 设计换图 | 发起方＝设计师 | 设计稿版本变更，自动 |

## 二、事件字段 schema（每条必带）

| 字段 | 必填 | 说明 |
|-----|-----|-----|
| 事件类型 | ✅ | 封闭枚举（上表 9 种），禁自由文本 |
| 时间戳 | ✅ | 行为发生时间，非记录时间；只有记录时间可用时须标记 |
| 站点外键 | ✅ | join key——1 站点＝度量基本单位 |
| 发起方角色 | ✅ | 需求 / 研发 / 设计 / 测试——归因钥匙：谁发起归谁 |
| 影响范围 | 变更/换图 | 文案 / 图片 / 结构 / 交互，作归因权重 |
| 关联单号 | 可选 | bug id / 需求版本 / 设计稿版本——可追溯＋自动采集锚点 |

## 三、三条铁律（决定成败）

1. **结构化**：类型枚举＋发起方角色，禁自由文本备注。前车之鉴：1029 条备注关键词只能捞到 5 条可判定记录。
2. **自动采集优先**：手填仅承诺类两条；行为事件全部从工具链进。前车之鉴：「是否延期」1003/1029 空白、上线打点覆盖仅 13%。
3. **定义写死**：提测后由需求方发起的任何内容改动（含文案微调）＝需求变更；设计师自发重制＝设计换图。由发起方字段天然区分，不靠人判断归类。

## 四、归因规则（滑期站点自动判定）

提测后时长按事件区间切分：事件 → 下一事件（或上线）的区间，归该事件发起方；提测 → 首事件的空窗归排期等待。

- 修复区间合计 → 研发
- 需求变更区间合计 → 需求侧
- 换图区间合计 → 设计侧
- 空窗合计 → 排期 / 等待

v1 按主因（占比最大块）归类整条；v2 可按区间占比分摊。准时条目免归因。

## 五、解锁的新观测（进 ④ 月度观测，不进头条数字）

| 观测 | 定义 | 回答 |
|-----|-----|-----|
| 修复轮次 | 提测后问题修复事件数 | 研发质量（代码侧的 ②） |
| 修复时长占比 | 修复区间 ÷ 提测后总时长 | 滑期里研发占几成 |
| 变更冻结时长 | 最后一次变更 → 上线 | 晚变更纪律、消化速度 |
| 变更频率 / 时段 | 每站点变更次数；提测前 vs 后 | 需求稳定性（提测后变更成本远高） |
| 空闲时长 | 无事件空窗合计 | 排期 / 资源等待——现在完全看不见 |

## 六、评估模型映射

①②③④、三个数、四识别全部不变。生效点：

- ① 产出 / 兑现：由发布流水线上线打点激活（解决当前 13% 覆盖）
- ③ 段内拆分（验收段＋发布段）：由「可交付」事件激活；提测后黑箱由行为事件打开
- ④ 🔄 变更观测：由归因数据激活（从占比升级为一等观测）
- ✅ 四识别：获得数据支撑——滑期多＋修复轮次多＝研发侧、滑期多＋变更占比高＝需求侧，可分开识别（届时可增第 5 条识别）

## 七、采集率红线

每个指标输出必须带 n 与采集率；采集率 < 80% 的指标只观测、不下结论（周期 / 准时率等头条数字尤其如此）。

## 八、读取与评估架构

**记录在 mico，评估在外面——由独立 Agent 只读外挂。** 小队的 issue 流转天然产生事件流，mico 的角色是**数据源**，不内嵌度量逻辑；分段、归因、剔除、报告全部由独立 Agent 读取计算。

| 留在 mico（数据源，天然产生） | 交给 Agent（评估层，只读） |
|-----|-----|
| 状态流转、issue 变更 | 分段计算（排队 / 开发 / 提测后 / 发布） |
| 承诺字段（计划设计稿交付 / 交付运营）排期时手填 | 归因规则（区间切分、主因判定） |
| 需求变更申报——需求方在流程里点一下 | 「需求变更」剔除口径 |
| 设计稿版本、bug 系统对接 | 周报 / 月报生成、四识别扫描、滑期提醒 |

不内嵌的理由：**口径是方法论资产**——缺戳排除、倒挂剔除、区间归因、双滑点等规则持续迭代，内嵌即被 mico 改版节奏绑架；**评估需要独立性**——考官不坐考场；**历史基线要连续**——Agent 同口径并算 bitable 1029 条历史＋mico 新事件，上线日基线延续而非归零。Agent 只读、不写回小队——报告推飞书文档 / 群，不在小队刷屏。

**API 硬门槛（先与 mico 确认，关系到归因能否成立）**——四要素必须接口可读：

1. 事件类型（枚举）
2. **发生时间**（≠ 更新时间——只有更新时间则分段全错）
3. 站点外键（join key）
4. **发起方角色**（≠ 操作人——只有操作人则归因断链）

即：对 mico 的诉求是「记录了，且 **API 可读**」。
